# Agent Note: batch-zip-generation

Status: implemented

## Problem

QR Code Forge could only export one code at a time, so bulk use cases — event badges, asset tags, per-table menu links — meant repeating the type-type-export loop N times. The styled pipeline (dot shapes, gradients, center art, Aztec/DataMatrix) already lived in the renderer, and the save path already went through a minimal IPC bridge; what was missing was a way to feed N payloads through that exact pipeline and hand back one archive.

## Decision

`src/core/batch.ts` exports `parseBatchInput(raw, limit=200)` → `{entries, issues}` plus `parseCsvLine`/`slugifyName`: RFC-4180-style CSV (double quotes, `""` escape) with a `\n` escape inside quoted fields for multi-line payloads; a first row that looks like a `name,content` / `content,name` header sets column roles for all rows (extra columns then ignored); without a header, 1 field = content, 2 = name,content, 3+ = `too-many-columns` issue (quote instead); blank lines and `#` comments are skipped; names are slugged and deduped (`name`, `name-2`, …), auto-derived from content when absent; problems never throw — they come back as line-numbered issues, and the entry cap reports once. `src/ui/batchModal.ts` owns the modal: live parse summary on every keystroke, PNG/JPEG/SVG + 256–4096 px pick (initialized from the store, deliberately not persisted), sequential `renderExport` per entry with progress text, jszip packaging (STORE for rasters, DEFLATE for SVG), then the existing `export:save` IPC with mime `application/zip` — electron/main.ts gained only a ZIP file-filter branch and an adaptive dialog title. `effectiveStyle` (center art forces EC H) moved from app.ts to store.ts so app and modal share it. Verified by 13 new parser unit tests (tests/batch.test.ts, 25 total) and scripts/smoke-cdp.mjs, a DevTools-protocol smoke test that drives the real built app headlessly (modal opens, summary counts, validation flags, Escape closes, preview renders) and prints text facts — no screenshots.
## Alternatives considered

**A dedicated batch tab replacing the single-editor UI** — rejected: doubles the UI surface for a flow that is "single editor × N inputs"; the modal reuses the live style settings and stays discoverable from the export row. **Rendering in the main process (sharp/canvas-node)** — rejected: the styled pipeline (qr-code-styling + render2d.ts) is renderer-owned and battle-tested; duplicating it natively would fork the visual truth. **Stream CSV with multi-line quoted records (RFC 4180 strictly)** — rejected: true multi-line records make line-numbered error reporting ambiguous and invite giant pasted payloads; one record per line plus the `\n` escape inside quotes covers multi-line payloads (vCard, email body) deterministically. **Unbounded entries with disk-backed ZIP** — rejected: no local filesystem API in the sandboxed renderer; a 200-entry cap with an explicit `limit-reached` issue keeps jszip memory bounded without new IPC. **fflate instead of jszip** — considered (smaller), but jszip's `generateAsync` progress callback drives the "Packing ZIP… N%" UX for free.
## Consequences

Bought: bulk export with zero new privileged surface (one file-filter branch in main.ts); the parser is pure and unit-tested, so CSV dialect changes are test-first. Cost/boundaries to know: (1) localStorage keys and the `forge.*` bridge are unchanged — batch settings (format/size chosen inside the modal) are intentionally NOT persisted; (2) one record per line means a literal newline inside an UNQUOTED field still splits records — quoting is required, the hint in the modal says so; (3) entries beyond 200 are dropped with a single aggregated issue, names beyond 40 chars are truncated by the shared slug rules; (4) export size list now reaches 4096 px — 4096² canvases (~67 MB) are fine on desktop but the modal never guards against many 4096px SVG entries with huge embedded logos. The CDP smoke script assumes the app runs with --no-sandbox --disable-dev-shm-usage --user-data-dir under this machine's restricted namespaces; on a normal desktop those flags are unnecessary.
